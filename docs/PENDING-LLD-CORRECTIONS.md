| 2 | `ItineraryConfiguration`'s original `OwnsOne` mapping for `DeparturePoint`/`ArrivalPoint` (`Location`) ignored `Type`/`DisplayName` — but `Location` has no parameterless constructor, so EF can't materialize it with 2 of 3 constructor params unmapped. | 3 | `BookingConfiguration` never mapped `Route` (`JourneyRoute`) at all, and the given SQL schema (§9.2) has no columns for it either — a real gap, not a workaround. First attempt (nested `OwnsOne` for Origin/Destination) also failed — EF's rule is that navigations to owned types can never satisfy a constructor parameter, ruling out nested owned types for any positional-record type. Fixed with a single `route` JSONB column via `HasConversion` (System.Text.Json), preserving full fidelity (Code/Type/DisplayName for both Origin and Destination, plus RouteType) without going through EF's owned-type materialization at all | `lld_booking.md` | §9.2 (add one `route JSONB NOT NULL` column to `bookings` table DDL), §9.3 (add the Route HasConversion mapping to BookingConfiguration) | Both the SQL DDL and the EF config sample need updating — genuine schema addition |
| 4 | `BookingConfiguration` never mapped `Passengers` (`PassengerCount`) at all, and the given SQL schema has no `adults`/`children`/`infants` columns either — same category of gap as Route. First attempt (`OwnsOne`) failed too — `OwnsOne` requires the owned type to be a class, and `PassengerCount` is a `readonly record struct`, so the compiler silently picked a wrong overload. Fixed with `ComplexProperty` (EF Core 8+'s correct API for struct-based value objects) | `lld_booking.md` | §9.2 (add `adults INT`, `children INT`, `infants INT` columns to `bookings`), §9.3 (add the Passengers ComplexProperty mapping) | Both the SQL DDL and the EF config sample need updating |
